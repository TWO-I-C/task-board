# 第二阶段 · 第 7 课：编辑后端任务名称

预计 45–60 分钟，其中阅读约 10–15 分钟。目标：给已有后端任务改名，理解“编辑框里的草稿”和“数据库已保存的值”的区别，并用页面、接口和 SQL 验证结果。

## 你目前的进度

阶段 1 已完成。阶段 2 已完成健康检查、前后端请求、任务读取与新增、PostgreSQL 持久化，以及完成状态修改。本课补充名称修改；后续再学习后端删除、账号与用户数据隔离。

## 开始前

保持 Postgres.app、`npm run server` 和 `npm run dev` 运行，打开 http://localhost:5173/。本课操作下方“本地学习实验：后端任务”，上方 localStorage 任务仍独立。

刷新后点击读取，每条任务右侧新增“编辑”按钮。点击后出现名称编辑框、保存名称和取消编辑。无需安装新依赖、重新建表或重新部署。

## 本课新增的行为

1. 点击编辑，把这条任务的名称复制到编辑框，形成草稿。此时没有修改数据库。
2. 点击保存，页面先校验名称，再发送 `PATCH /api/tasks/任务ID`，正文只包含 title。
3. 后端再次校验，通过后执行参数化 UPDATE。收到成功响应后，页面重新 GET 列表。
4. 输入为空或只有空白时提示错误，保留原名称。有效名称首尾空白会被去掉；名称最长 200 个字符。
5. 点击取消编辑或在输入框按 Escape，丢弃尚未提交的草稿。保存请求进行中不能取消，取消也不会撤销已经成功的数据库写入。

编辑期间其他任务的编辑、勾选和新增暂时禁用；“读取后端任务”仍可使用，并保留编辑框文字。

## 配套阅读（10–15 分钟）

- [MDN：表单数据校验](https://developer.mozilla.org/zh-CN/docs/Learn_web_development/Extensions/Forms/Form_validation)：阅读“什么是表单数据校验”和“不同类型的表单数据校验”，重点理解客户端校验与服务器端校验的区别。暂时跳过后面的长代码示例。
- [PostgreSQL 18：Updates](https://www.postgresql.org/docs/18/tutorial-update.html)：复习 SET 修改哪些列、WHERE 选择哪些行。本课把上一课的 completed 换成 title。

页面校验能尽早告诉用户哪里填错，但用户也可以直接发送 HTTP 请求，所以后端仍必须独立校验。数据库自身的约束继续保留。

## 对照接口和 SQL

改名请求示例：

```json
{ "title": "练习 PATCH 20 分钟" }
```

完成状态仍使用上一课的 `{ "completed": true }` 或 false。当前接口约定每次只改一个字段；同时传 title 和 completed 会返回 400，不修改任何字段。ID 在 URL 中指定，不能用请求正文更改。

改名使用的 SQL 模板：

```sql
UPDATE tasks
SET title = $1
WHERE id = $2
RETURNING id, title, completed;
```

`$1` 是新名称，`$2` 是 ID，由 Node.js 驱动传入，不直接复制到 psql 执行。SET 只修改 title，因此 ID、完成状态、创建时间和任务总数保持不变。同名任务仍由各自的 ID 区分。

可在 Chrome 开发者工具的 Network → Fetch/XHR 中观察保存动作：先 PATCH（正文是 title），成功后再 GET。编辑框内输入文字或取消编辑不会发出改名请求。

## 五项独立验收

使用上一课两条同名的“练习 PATCH”。如已没有同名任务，可新建两条作为练习。先把第一条设为已完成，记录两条的 ID、总数和已完成数。

1. **正常改名与同名隔离**：编辑第一条，输入首尾带空格的“  练习 PATCH 20 分钟  ”并保存。列表和 SQL 显示去掉首尾空格的新名称，另一条仍叫“练习 PATCH”。第一条 ID 不变、仍已完成；总数和已完成数不变。
2. **无效名称**：编辑第一条，清空输入后保存，再试只输入空格。都应提示错误，编辑框保持打开，列表及数据库仍是原先保存的名称。最后取消编辑。
3. **取消编辑**：输入“这次不保存”，点击取消编辑，名称不变。再试一次，改用 Escape 取消，结果相同。直接 SQL 查询也不能出现“这次不保存”。
4. **刷新与重启**：刷新页面并读取，再只重启 Node.js 后端并读取。第一条仍叫“练习 PATCH 20 分钟”，ID、完成状态及数量保持一致。对照下方 SQL 查询。
5. **失败与恢复**：编辑第一条，把草稿改为“恢复连接后保存”。在 Postgres.app 停止数据库，再点击保存，应出现失败提示，编辑文字保留，不宣告改名成功。重新启动数据库，点击“读取后端任务”，列表仍是旧名称，编辑框仍是新草稿。确认后再点击保存，SQL 才变为新名称，其他字段仍不变。

每次用 ID 对照同一条记录，不能只按名称判断：名称正是本课要修改的字段。

在空闲终端运行只读查询：

```bash
/Applications/Postgres.app/Contents/Versions/latest/bin/psql -X -h 127.0.0.1 -p 5432 -U two-i-c -d task_board -c "SELECT id, title, completed FROM tasks ORDER BY created_at, id;"
```

## 补充实验：直接调用接口也会校验（约 3 分钟）

前面的无效名称被页面拦住了。现在绕过页面，用终端向自己的本地接口发送空白名称：

```bash
curl -i -X PATCH http://127.0.0.1:3001/api/tasks/validation-check \
  -H 'Content-Type: application/json' \
  -d '{"title":"   "}'
```

预期 HTTP 400，说明后端自己拒绝了无效名称。本接口先校验内容再查询数据库，因此这个实验用的 ID 不需要存在，也不会写入数据。`curl` 是发送 HTTP 请求的命令；`-i` 显示响应状态和标头，`-X` 指定方法，`-H` 设置标头，`-d` 提供正文。

## 失败时怎样判断

- 后端明确拒绝请求（例如 400、404）：不能显示保存成功。
- 连接断开或请求超时：页面可能无法确认最终写入结果，应恢复后重新读取核对，不自动重复提交。
- PATCH 已返回 200，随后 GET 失败：名称已经被后端确认保存，只是列表未能更新；页面会明确说明并保留编辑文字，重新读取后再决定保存或取消。

编辑框的文字是当前页面中的草稿，刷新页面会丢失未提交草稿；数据库中的已保存名称不受影响。读取列表只查询数据库，不会把草稿写进去。

## 对照源码

- `src/BackendTasks.jsx`：editing 保存草稿；saveTitle 做页面校验并发送 PATCH；失败保留草稿，重新读取后允许核对操作。
- `server/index.js`：validatedTitle 供新增和改名共同使用；PATCH 校验字段并选择相应的修改操作。
- `server/database.js`：setTaskTitle 只更新 title，保留任务其他字段。
