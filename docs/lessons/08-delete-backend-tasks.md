## 开始前

保持 Postgres.app、`npm run server` 和 `npm run dev` 运行，打开 http://localhost:5173/，在下方“本地学习实验：后端任务”点击读取。每条任务旁新增“删除”按钮。

点击删除会先在页面内出现确认区，显示任务名称和完成状态。点击“取消删除”或在确认区按 Escape，不会发送请求；点击“确认删除”才执行删除。请求进行中按钮暂时禁用。本课不需要安装依赖或重新建表。

本次删除直接移除数据库记录，任务板没有撤销功能。验收使用下面专门新建的练习任务；Git 保存代码，不能恢复删除的数据库记录。

## 配套阅读（约 10 分钟）

- [MDN：DELETE](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Reference/Methods/DELETE)：看开头和成功响应。本项目选择 200 并返回 JSON；其他接口也可能使用没有响应正文的 204。
- [PostgreSQL 18：Deletions](https://www.postgresql.org/docs/18/tutorial-delete.html)：理解 DELETE FROM 与 WHERE。只阅读无 WHERE 的示例，不在任务数据库中执行。

## 一次确认删除经过了什么

点击删除 → 页面显示确认区 → 点击确认 → 浏览器发送 DELETE → 后端按 ID 删除 → 数据库返回被删除的记录 → 后端返回 200 → 页面 GET 最新列表并重新计数。

请求示意（任务 ID 放在 URL 中，不需要 JSON 正文）：

```http
DELETE /api/tasks/目标任务ID
```

SQL 模板：

```sql
DELETE FROM tasks
WHERE id = $1
RETURNING id, title, completed;
```

- `WHERE id = $1` 指定唯一记录。同名任务由各自 ID 区分。
- `RETURNING` 返回刚被删除的记录，便于后端确认删了哪条；它不会让记录继续留在表里。
- 找不到 ID 时，SQL 删除 0 条，后端返回 404；不会转而删除别的记录。
- 没有 WHERE 的 DELETE 会删除表中所有行。本课只解释这个结果，不执行这种语句。

`$1` 由 Node.js 驱动传入，以上是程序模板，不是让你直接复制到 psql 执行的完整命令。

## 五项独立验收

先在下方新增两条完全同名的“删除练习”，将第一条标记为已完成；另建一条未完成的“删除恢复练习”。用下方 SQL 记下这三条的 ID，并记录总数 N、已完成数 C。

1. **取消删除**：对第一条“删除练习”点击删除，确认区显示其名称和“已完成”。点击取消，任务、N、C 和 SQL 结果都不变。可再试一次 Escape。打开 Network → Fetch/XHR 观察，这一步没有 DELETE 请求。
2. **确认删除与同名隔离**：再次点击第一条的删除并确认。它消失，另一条同名任务仍在；总数变成 N−1，已完成数变成 C−1。SQL 查不到第一条 ID，但能找到另一条 ID。
3. **刷新和重启**：刷新页面并读取，再只重启 Node.js 后端并读取。已删除任务不会回来，另一条同名任务仍在，数量与第 2 项一致。
4. **数据库停止时删除**：先读出列表，再停止 Postgres.app 中的数据库服务。尝试删除“删除恢复练习”并确认。页面应提示 HTTP 503，不能显示删除成功，也不能提前把它当成已经删除。此时显示的是上次读到的列表，需恢复后核对。
5. **恢复后核对再删除**：启动 PostgreSQL，点击读取，“删除恢复练习”应仍存在，ID 不变。再次删除并确认后，SQL 中才找不到它；总数变成 N−2，已完成数仍为 C−1，因为这次删除的是未完成任务。

只读查询（在空闲终端执行）：

```bash
/Applications/Postgres.app/Contents/Versions/latest/bin/psql -X -h 127.0.0.1 -p 5432 -U two-i-c -d task_board -c "SELECT id, title, completed FROM tasks ORDER BY created_at, id;"
```

如果已有同名练习记录，请用本次记录的 ID 对照。不要仅凭标题消失与否判断是否删对了任务。

## 观察请求与错误

在 Chrome 开发者工具 Network → Fetch/XHR 中，确认删除后应看到：

1. DELETE 请求，地址末尾为目标任务 ID，成功状态为 200。
2. Response 中的 task 为被删除的记录。
3. 随后的 GET /api/tasks 返回更新后的列表。

本课按以下方式处理不同结果：

| 结果 | 页面应如何理解 |
| --- | --- |
| 取消确认 | 没有发出 DELETE，不修改数据库 |
| DELETE 返回 200，GET 也成功 | 删除已确认，显示最新列表和计数 |
| DELETE 返回 200，随后 GET 失败 | 后端已经确认删除，只是列表未刷新；提示重新读取，不再重复删除 |
| DELETE 返回 404 | 目标记录已不存在；可能被另一个页面删除，重新读取即可核对 |
| 连接失败、超时或数据库报错 | 最终结果可能无法确认，恢复后先读取；不自动重试删除 |

第五项能读到原记录，是因为实验明确在请求之前就停止了数据库。不能把所有网络失败都解释为“肯定没删掉”：有时删除已完成，只是成功响应没有送达浏览器。

重复删除同一个 ID，第一次可能 200，第二次可能 404，但目标记录最后都不存在。这说明“相同请求的最终效果一致”不要求每次返回完全相同的状态码。

## 对照源码

- `src/BackendTasks.jsx`：deleting 保存待确认的任务；确认后发送 DELETE，取消不发送；失败后要求重新读取。
- `server/index.js`：单条任务路径支持 PATCH 和 DELETE；解析 ID 后选择操作，等待数据库完成后响应。
- `server/database.js`：deleteTask 使用带 WHERE 的参数化 DELETE，并返回被删除的行。
