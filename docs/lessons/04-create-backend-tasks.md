# 第二阶段 · 第 4 课：向后端新增任务

预计 60–90 分钟，包含 10–15 分钟阅读。目标：用 POST 发送数据，理解前后端都要校验，以及“刷新页面”和“重启后端”对数据的不同影响。

阶段 1 已完成；阶段 2 前三课已完成健康检查、页面调用接口和读取任务。本课加入新增，后续接入 PostgreSQL，再逐步加入账号与用户隔离。

## 本课的数据流与约定

输入后端任务名称 → 前端检查 → POST `/api/tasks` → 后端再次检查 → 生成 ID、写入内存 → 返回 201 → 前端 GET 列表并显示。

| 操作 | 请求 | 成功响应 |
| --- | --- | --- |
| 读取 | `GET /api/tasks` | `200` 与 `{ "tasks": [...] }` |
| 新增 | `POST /api/tasks`，正文 `{ "title": "学习 POST 请求" }` | `201` 与 `{ "task": { "id": "后端生成的唯一值", "title": "学习 POST 请求", "completed": false } }` |

POST 请求还有 `Content-Type: application/json` 请求头，说明正文格式。后端清理名称两端空格，要求名称是非空文本，最长 200 个字符。ID 和初始完成状态由后端决定；同名任务允许存在，但 ID 不同。

本课中的 `GET` 用来读取，`POST` 用来新增。只在浏览器地址栏打开接口会发送 GET，不会新增。

## 配套阅读（10–15 分钟）

1. [MDN：使用 Fetch](https://developer.mozilla.org/zh-CN/docs/Web/API/Fetch_API/Using_Fetch)，只读“支持的请求参数”和“上传 JSON 数据”。重点辨认 `method`、`headers`、`body`，不用跟做上传文件或凭据部分。
2. [MDN：201 Created](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Reference/Status/201)，看开头说明：服务器已成功创建资源。

在 `src/BackendTasks.jsx` 找到这一段，逐项用自己的话解释：

```js
fetch('/api/tasks', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title }),
  signal: AbortSignal.timeout(5000),
})
```

最后一行把本次等待限制为 5 秒。超时只表示前端没有及时收到结果，不能保证后端一定没有写入。页面会保留输入并提示先读取确认；本课不会自动重发 POST。

## 五项独立验收

1. **正常新增**：在下方输入“学习 POST 请求”，点击“新增到后端”。出现“新增成功”，列表增加一条未完成任务，名称输入框清空。此时共 3 项，已完成 1 项。上方个人任务数量不变。
2. **拒绝空内容**：输入几个空格后提交，提示名称要求，后端数量仍为 3。再用下面的 curl 实验绕过前端检查，确认后端同样拒绝。
3. **刷新仍能读回**：刷新浏览器，再点击“读取后端任务”，刚新增的任务仍在，共 3 项。原因是后端进程一直在运行。
4. **断开时不假报成功**：只停止后端，在下方输入“断开时尝试新增”，提交。应显示结果未确认或连接失败，保留输入，不显示新增成功。不要连续重复点击。重新运行后端，先点击“读取后端任务”确认当前记录。
5. **重启丢失内存数据**：第 4 项重启后读取，应只剩两条初始示例，“学习 POST 请求”消失。现在提交保留的“断开时尝试新增”，应成功并变成 3 项，说明恢复后仍能使用。

若在页面中操作过其他新增，按自己实际新增次数判断数量。修改后端源文件也会触发 `node --watch` 重启，效果与手动重启类似。

## 绕过前端，验证后端检查

在第三个空闲终端执行：

```bash
curl -i http://127.0.0.1:3001/api/tasks \
  -X POST \
  -H 'Content-Type: application/json' \
  -d '{"title":"   "}'
```

`-i` 显示响应头；`-X POST` 选择请求方法；`-H` 设置正文格式；`-d` 是要发送的正文。

预期：HTTP `400`，正文包含“任务名称不能为空，且必须是文本”。重新读取列表，数量不增加。这个请求直接到后端，没有经过页面输入框，证明后端校验不能只靠前端。

可在第 1 项提交前打开 Chrome 开发者工具的 Network（网络），筛选 Fetch/XHR：一次成功新增会先出现 POST `201`，随后 GET `200`。这里只观察请求，暂时不用学习全部开发者工具。

## 数据究竟存在哪里

| 操作 | 页面内存中的后端列表 | 后端进程内存中的任务 | 上方 localStorage 个人任务 |
| --- | --- | --- | --- |
| 刷新浏览器 | 重置，需再次 GET | 保留 | 保留 |
| 停止并重启后端 | 在重新请求前可能仍显示旧结果 | 新增记录丢失，重新加载初始示例 | 保留 |

上方本地任务、下方页面状态、后端内存，是三处不同的存放位置。本课还没有写入数据库。

还要区分：后端已经返回 201，但随后 GET 列表失败时，页面会提示“后端已确认新增成功，但列表未能更新”。此时应该先读取列表，不要再新增一遍。
